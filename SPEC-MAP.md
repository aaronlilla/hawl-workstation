# Hawl Workstation: SPEC-MAP

Every SPEC line S4 to S50 from the m2 contract (`E:\hawl-platform\_work\2026-10-18-scenarios\m2-contract.md`, section 1), with the workstation screen that shows it, where the data comes from, and how it will be proven in the running app. Status is `todo` for all 47 lines (2026-10-19): nothing is built.

How to read it:
- Screen: the names in the table in [ARCHITECTURE.md](ARCHITECTURE.md) section 2 ("The screens"): Sidebar tree, Pane chip, Job drawer, New job form, Needs tray, Messages, Yard console (with tabs Menu, Foreman, Ledger, Team check, Doctor, Sites, Setup), Settings, Map view, Phone web page, Phone app. Every name here is in that table and the other way round. Names are proposals until built.
- Data source: relay route or tool from the contract (section 3 of the contract). Contract routes are not shipped on hawl-platform origin/main as of 2026-10-19 (plan), so every row depends on the m2 builders landing the matching relay piece.
- Proof: what a person does in the running app and what must be on screen. Each proof is run in the real app with a screenshot, against a local or staging relay. Where a proof needs a second yard, a second site or a phone, it says so.
- Milestone: M0 fork and rebrand, M1 sign-in, M2 site/yard/haul tree, M3 agents, M4 approvals and proof, M5 presence/rooms/yard console, M6 phone, M7 release (from `PROJECT.md`). The milestone is when the workstation side of the row is built; build order is by milestone, then by line number.
- Built by: WS = this fork; relay = the m2 builders' relay pieces (this fork never edits them); peer CLI = a change in the hawl-platform CLI owned by another builder; web = pieces in hawl-platform `apps/web` (contract N2 web push and `apps/web/public/sw.js`, H2 `NeedsCards`, X5 `TownCanvas`). The phone path in the contract is the web page plus web push, so "Phone web page" is the screen for phone proofs. The native `hawl-mobile/` app ("Phone app", plan decision 2026-10-19) is a separate later piece; no S line is proven through it yet.
- Proof class, which says how far the running app can prove the row:
  - A: the whole behavior is shown and checkable in the running app.
  - A*: needs a faked or controlled dependency to hit both sides (S14: a stub for the classifier's confidence).
  - R: the relay enforces the rule and its own test (T1 in the contract) proves it; the app proof is that the app shows the refusal or result.
  - R*: as R, and the behavior depends on a relay piece that does not exist yet (S15: the answering service).
  - X: cannot be proven by one run of the app: S28 is proven in the chat client (the app shows only the resulting job), S49 is a five-day soak, and the 30-day deletion half of S25 is a relay test only.
  - "timed": the proof includes a clock limit (S36, S37, S38 within the stated time).

Counts by proof class: A 27 (plus 3 timed), A* 1, R 12 (plus S25 with a relay-only part), R* 1, X 2 (S28, S49). By milestone: M2 2 (S4, S5), M3 4 (S16, S17, S23, S24), M4 23, M5 18 (S47 moved here), M6 0 (the native phone app has no S line).
